# アーキテクチャ

ccplantは、操作するクライアント、制御を行うAPI、実際にコードを扱うエージェントセッションを分離しています。

```text
┌──────────────────────────────┐
│ Web UI / Native app / API client │
└──────────────┬───────────────┘
               │ HTTPS / SSE
┌──────────────▼───────────────┐
│ ccplant backend              │
│ Auth · Sessions · Routing    │
└───────┬──────────────┬───────┘
        │              │
┌───────▼───────┐  ┌───▼────────────────┐
│ KV / metadata │  │ Session Manager     │
└───────────────┘  └───┬────────────────┘
                       │
                ┌──────▼──────────┐
                │ Agent sessions  │
                │ Local / K8s     │
                └─────────────────┘
```

## リクエストの流れ

1. クライアントがバックエンドの `/start` へセッション作成を要求します。
2. バックエンドまたはSession Managerが隔離されたAgentAPIプロセスを起動します。
3. バックエンドがセッションIDと実行先の対応を保持します。
4. クライアントはセッションID付きURLを使い、バックエンド経由で会話・イベントを送受信します。

## データと状態

セッションのメタデータはKVストアへ保存できます。実行中プロセスの状態と会話履歴の永続化は別の関心事です。再起動をまたいだ構成は[KVストア](../kv-store)と[セッション永続化](../acp-session-persistence)を確認してください。

## デプロイモデル

- **Docker Compose**: 評価とローカル開発向け
- **分離Helm Chart**: backendとfrontendを独立運用する既存構成向け
- **統合ccplant Chart**: 新規のKubernetes環境に推奨
- **外部Session Manager**: APIとエージェント実行基盤を分離する大規模構成向け
