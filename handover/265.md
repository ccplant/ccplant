## 1. ユーザーの要求(最重要)

Codex device auth(`codex login --device-auth` の実行)は:

- **in-process 実行は完全に禁止**(Fly の fake k8s client でも、実クラスタでも)
- **常に ESM (External Session Manager) の control tunnel 経由**で、
  **session manager が作る attempt 用の短命 Pod** 上で実行すること

ユーザーの言葉: 「legacy in-process 自体完全にやめてほしい。常に session control tunnel 経由になってほしい」

設計文書: `docs/codex-device-auth-workload.md`(本 PR で Status を Implemented (MVP) に更新)

### 実装内容

- **親(API)側** `backend/internal/infrastructure/esmcontrol/codex_device_auth.go`
  - `CodexDeviceAuthLauncher`(`codexauth.WorkloadLauncher` 実装)
  - 登録済み manager 一覧(session runner registry)から connected なものを選択
    (優先順位: `codex_device_auth_v1` capability > default > 最新 heartbeat)
  - `Tunnel.Do` で `POST /api/v1/codex-device-auth` を投げる(session delete と同じ経路)

  - `sessionmanagerapi.Handler` の `/codex-device-auth` ルート
  - router.go の `sessionManager.(WorkloadLauncher)` fallback(in-process 起動)
- **server.go**: `esmControlTunnel != nil && sessionRunnerStore != nil` なら常に tunnel launcher を使う
- **テスト**: `esmcontrol/codex_device_auth_test.go`(launcher 挙動)、

### 未完了(ブロッカー)

**dev ESM の新 pod が CrashLoopBackOff 中。E2E 検証(device auth の 202 → waiting_for_user → cancel)はここで止まっている。**

クラッシュ原因(新 pod `ccplant-session-agentapi-proxy-session-manager-86bbb66d95-8g46c` の log):

```
Error: purge stock sessions on session-manager startup: failed to resolve allocated
runners for purge protection: decode parent heartbeat: invalid character '<' looking
for beginning of value
```

- `KubernetesSessionManager.fetchAllocatedRunnerIDs`(kubernetes_session_manager.go ~1272)が
  startup 時に `POST {upstream}/internal/session-managers/{managerId}/heartbeat` を呼ぶ
- upstream = `https://dev.ccplant.com`(Cloudflare Worker 経由)がこの **POST /internal/session-managers/...** を
  Fly API にルーティングせず **HTML(SPA/login)を返す**ため JSON decode に失敗
- **旧 pod(現役, dcada963 image)も同じ decode error を 30 秒ごとに出している**(旧コードは非 fatal なので稼働継続)
- GET `/internal/external-session-manager/control/commands` は dev.ccplant.com 経由で通っている
  (CommandWorker の poll は成功 → これが「manager が connected に見える」理由)

## 6. ハマりどころ(今回判明済み)

- Fly 上の API は k8s config がないと **fake client に fallback** する。fake は `WorkloadLauncher` を実装しているので
  device auth が「成功したことに」なり永遠に `starting` → これが元々のバグ(PR #265 旧 revision の発端)
- runner モードの ESM は HMAC secret が無いと **転送ルート全体が登録されない**(NewHandlers が early return)。
  ControlWorker は connectionToken に fallback して署名するので「コマンドは届くが 404/401」になり原因が分かりにくい
- ESM の `AGENTAPI_SESSION_MANAGER_API_URL` が親を指すと、control command が**親に対して実行**される
  (ヘッダの Authorization は Tunnel 側で strip されるので親は 401)。必ず `http://127.0.0.1:8080` 等 自分自身を指すこと
- `dev.ccplant.com`(Cloudflare Worker)は `GET /internal/external-session-manager/*` は通すが
  `POST /internal/session-managers/*` は HTML を返す(現在不具合の原因)
- egress proxy(127.0.0.1:3128)経由の curl は dev.ccplant.com を 307 /login に飛ばされることがある
  (pod 内からの直接アクセスとは挙動が違うので、curl の結果だけで判断しないこと)
- publish-dev-charts の chart version は「0.3.0-dev.ccplant.<sha7>」、image tag は「dev.ccplant.<sha40>」
